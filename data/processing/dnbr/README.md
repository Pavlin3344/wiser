# dNBR worker (Фаза 3)

Тежест на изгарянето след пожар. Консумира `analysis.tasks` (двойка Sentinel-2 сцени —
преди и след), смята dNBR, записва растера в MinIO `processed-products/dnbr/` и
обобщението в PostGIS таблицата `burn_severity`.

Контракт: [`shared/schemas/message-contracts.md`](../../../shared/schemas/message-contracts.md),
раздел „Фаза 3". Невалидна задача → `analysis.dlq`.

## Какво е dNBR

**NBR** = (NIR − SWIR2) / (NIR + SWIR2), от канали **B08** и **B12**. Живата растителност
отразява силно в NIR и слабо в SWIR2; изгорялата почва прави точно обратното. Затова
разликата между двете дати мери щетата:

```
dNBR = NBR_преди − NBR_след
```

Праговете са стандартните на USGS (Key & Benson 2006), а класовете са 1–6 — същата скала
като `fwi_class` и `risk_class`, за да няма трета конвенция в проекта:

| клас | dNBR | значение |
|:-:|---|---|
| 1 | < −0.10 | възстановяване (по-зелено отпреди) |
| 2 | −0.10 … 0.10 | без промяна |
| 3 | 0.10 … 0.27 | ниска степен |
| 4 | 0.27 … 0.44 | умерено-ниска |
| 5 | 0.44 … 0.66 | умерено-висока |
| 6 | > 0.66 | висока |

За „изгоряло" в отчета се броят класове **3–6**. Възстановяването и липсата на промяна не
са щета — иначе всяка гора би излизала пострадала.

## Площи

Хектарите се смятат по ред на растера, а не с една стойност за целия кадър: при
географски координати градус дължина се смалява на север, така че пикселите горе покриват
по-малко земя. Точно това число излиза после като „толкова декара са изгорели".

При метрична проекция площта е константа и се взима направо от трансформацията.

## Setup (Python 3.11 — заради rasterio)

```bash
cd data/processing/dnbr
python3.11 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
```

Изисква локалния стек (`docker-compose.dev.yml`) и приложена миграция
`db/postgres/migrations/V3__burn_severity.sql` (Flyway я пуска сам).

## Пускане

```bash
# терминал 1 — worker-ът слуша
python worker.py

# терминал 2 — синтетична двойка сцени с изгоряла четвъртинка
python mock_publisher.py                 # валиден сценарий
python mock_publisher.py --fire-id 7     # вързан за конкретен пожар
python mock_publisher.py --broken        # липсваща сцена → analysis.dlq
```

Проверка:
```bash
docker exec wiser-postgres psql -U wiser -d wiser -c \
  "SELECT fire_id, pre_date, post_date, round(burned_hectares) AS ha_burned,
          round(analysed_hectares) AS ha_total, round(mean_dnbr::numeric, 3) AS mean_dnbr
   FROM burn_severity ORDER BY computed_at DESC;"
```

Mock-ът изгаря точно четвъртинка от кадъра, така че очаквай ~25% изгоряла площ, всичко
във висок клас.

## Тестове

```bash
pip install -r ../requirements-dev.txt
python -m pytest
```

Без мрежа и без база: сцените се пишат като истински GeoTIFF-ове във временна папка, а S3
клиентът и връзката към базата са фалшиви. Покрити са всички граници между класовете,
сметката за площ (включително че пикселът се смалява на север), редът на каналите и това,
че повторен анализ обновява реда вместо да трупа нов.

`test_fetch_scene_pair.py` покрива решенията, които producer-ът взима **преди** да е свалил
каквото и да е — избор на дата, прозорци, размер на растера и разпознаването на празен
кадър. Тъкмо те могат да мълчат вместо да гръмнат.

## Ограничения

Сцена над **20 мегапиксела** се отхвърля с ясна грешка (→ `analysis.dlq`), защото не се
събира в паметта на контейнера. Таванът се вдига с `DNBR_MAX_MEGAPIXELS`, но заедно с
`mem_limit` на `worker-dnbr` — иначе контейнерът умира по OOM, а убит контейнер не е
потвърдил съобщението: то се връща в опашката и следва цикъл от рестарти.

Истинското решение за големи сцени е обработка на парчета (windowed read). Не е направено,
защото днешните сцени са далеч под тавана.

## Реални сцени: `fetch_scene_pair.py`

`mock_publisher.py` е синтетичен — за истински анализ има `fetch_scene_pair.py`. Намира
къде е горяло по детекциите в `active_fires` (клъстер с `ST_ClusterDBSCAN`), избира
най-близките достатъчно безоблачни сцени преди и след пожара, сваля **само B08 и B12** и
публикува задачата.

Пуска се в мрежата на compose — MinIO (9000) и RabbitMQ (5672) са вързани за loopback на
хоста, така че отвън не се стига до тях:

```bash
cd infra/docker
# показва кой пожар и кои дати би взел, без да харчи квота и без да пише никъде
docker compose -f docker-compose.yml -f docker-compose.jobs.yml \
  run --rm dnbr-scene-fetcher \
  python dnbr/fetch_scene_pair.py --since 2026-08-15 --until 2026-08-21 --dry-run

# същото, но наистина
... --since 2026-08-15 --until 2026-08-21

# ръчно зададен участък, без търсене в базата
... --bbox 25.60 41.80 25.80 41.95 --pre 2026-08-08 --post 2026-08-22
```

Иска `COPERNICUS_CLIENT_ID` / `COPERNICUS_CLIENT_SECRET` — същите, които ползва и
`ingestion`.

Три неща, които не са очевидни:

- **Датите идват от каталога, не от прозореца.** Празен отговор на Process API не е
  грешка — връща черен кадър, който минава през целия pipeline и завършва с ред от нули
  в `burn_severity`. Затова първо се пита каталогът кои дни изобщо имат снимка, и чак
  тогава се сваля точно този ден. Като страничен ефект датата в `burn_severity` е
  истинската дата на снимката.
- **Близостта до пожара бие облачността.** Сцена отпреди месец с 0% облаци мери и растежа
  на растителността, не само щетата; затова облачността е праг (`--max-cloud`), а изборът
  между приемливите е по близост.
- **`SentinelFetcherService` не става за източник.** Той сваля B04 + B08 за NDVI, а dNBR
  иска B08 + B12 и го проверява — нито една вече свалена сцена не е годна.

## Отворено

Това не е producer-ът, който контрактът предвижда. Онзи е на бекенда и се пуска сам,
когато пожар угасне (раздел 10, „остава да се реши"); скриптът тук се пуска на ръка и
служи, докато другият го няма. Съобщението е едно и също, така че бекендът може да го
замести без промяна в worker-а. Това е разговор с Ицо, не блокира worker-а.
